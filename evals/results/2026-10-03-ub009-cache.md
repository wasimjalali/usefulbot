# UB-009 evals: prompt cache across a permission flip and midnight (2026-10-04)

## The question

UB-009 puts per-turn facts in the last system block ("This turn": date, time zone, permission, folder, model). A change there sits behind the shared instructions and could cost prompt-cache hits. The plan (section 3) makes a cache eval the gate: if it shows a regression, date, permission and folder move to a user-role line.

## What ran

- **App:** Useful Bot Dev (same tree as `main` `a8dcb41`), launched with the router payload probe and `TZ=Africa/Lagos`:
  ```sh
  open -g --env UB_PAYLOAD_PROBE_DIR=<dir> --env TZ=Africa/Lagos "$HOME/Applications/Useful Bot Dev.app"
  ```
  Lagos is UTC+1, so its midnight fell at 01:00 Berlin. That made a real day change possible with no relaunch mid-run, so no service restart sits in the data.
- **Bot and model:** Test Bot on GLM 5.3 Flash (OpenCode Go, effort high). The session was fresh: the bot cleared its own history first.
- **Turns:** 12 one-line turns, no tools (`turns-cache.json`), sent with `run-turns.py`:
  - C01 to C04 in Auto;
  - then the composer's permission menu set to Read only;
  - C05 to C08;
  - C09 to C12 after 00:00 Lagos, sent automatically 30 s after the date changed.
- **Evidence:**
  - the router's `upstream_usage` lines for the session (`cache-usage.jsonl`: input, cached input, output, time to first byte);
  - the request bodies from the payload probe, diffed request by request.
- **Cost:** 12 short turns plus one clear on the OpenCode Go plan already paid for. No per-token spend.

## What the run shows

1. **The permission flip and the date change cost nothing measurable.** The cached prefix held at 4,864 tokens across both, and rose to 7,296 at C12.
   - Caveat: the changed text sits near the end of the system message (characters 8,920 to 8,975 of 9,140, about 2.3k tokens), and the tools array is about 7k tokens. How the provider orders them in its prompt isn't visible. Since the cache kept 4,864 tokens across the change, either the tools come first or the provider isn't strictly prefix-based. So this run shows the change didn't shrink the cache GLM actually gives. It can't show what a strict whole-prefix cache would lose.
2. **The provider caches in 2,432-token blocks, best effort.** 4,864 is two blocks and 7,296 is three. The first three turns got no cache at all, and the steady state is about half the prompt. That's the provider's behaviour, since the requests themselves are prefix-stable.
3. **The first-chat line changes the system message between turn 1 and 2.** That's one expected miss, by design.

## Conclusion

No regression, so the gate passes. The per-turn facts stay in the "This turn" system block, and nothing moves to a user-role line. One run on one provider, so the numbers say "no visible cost" rather than "zero cost". A provider with whole-prefix caching (Anthropic's cache breakpoints, for example) would show the true cost of a mid-system change more clearly, if that ever matters.
